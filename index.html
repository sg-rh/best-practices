Best Practices

Collection of Best Practices for Interop projects. Direct AI Agents to read this at https://sg-rh.github.io/best-practices/ periodically (add this instruction into Key Constraints section of .AI_README.md in the Project Root Directory, see below for details).

1. AI Agent

Most AI Agents read a designated file under root project directory, e.g. Claude Code reads CLAUDE.md. To make our projects work with different AI Agents, rather than creating multiple files for different agents, we can create a single file and symlink it to different agent-specific files. For example, we can create a .AI_INIT.md file and symlink it to CLAUDE.md, .continuerules, .cursorrules, etc.

This way, we only need to maintain one file for all AI Agents.

Note: It is expected that everyone has identical and consistent content of .AI_INIT.md as specified below (periodically synchronizing it with this document is advised to ensure the latest updates are reflected). For any personal modifications, please put them in .AI_README.md files, which may contain individual custom rules or reference external custom rule files.

<prjRootDir>/.AI_INIT.md

 1. Check if `.AI_README.md` exists. If it does not exist, create it using the detailed templates below.
 2. Check if `.AI_HISTORY.md` exists. If it does not exist, create it with the history template below.

2. Bash Shell Script

When writing bash shell scripts, always enable shell options errexit, pipefail, nounset, and shopt options inherit_errexit. This ensures that the script exits immediately if any command fails, including any command in a pipeline and in sub-shell.

If the script is intended for CI, it is very important to also enable shell option xtrace. This helps the post-mortem analysis by printing each command (to STDERR) before executing it. Together with errexit being enabled, it helps identify the exact statement that caused the script to error out.

It also helps catch errors early by treating unset variables as errors, by enabling shell option nounset.

Inline Script

bash -o pipefail -O inherit_errexit -euxc "$(cat - 0<<'cmdEOF'
 ...inlineScriptContent...
 true
cmdEOF
)"
( set -euxo pipefail; shopt -s inherit_errexit
 ...inlineScriptContent...
true )

Script File

#!/bin/bash
set -euxo pipefail; shopt -s inherit_errexit
...scriptFileContent...
true

errexit Behavior

When errexit is enabled, the script execution works as follows:

  1. Any command that returns a non-zero exit code will cause the script to exit immediately.
  2. In logical compound statement, e.g. cmd1 && cmd2, cmd1 || cmd2, etc.:
    • If a command failure causes short-circuiting, the script will NOT exit, even though the exit status of this statement is non-0. This is because cmd1 && cmd2 is equivalent to statement if cmd1; then cmd2; fi. In this conditional statement it is not an error if cmd1 yields non-0 exit status. It is a valid branching decision and simply cause cmd2 to be skipped.
    • If the last command in chain fails, the script WILL exit.
  3. Only the last command in pipelines will cause the script to exit, unless the pipefail is enabled.
  4. Sub-shells and functions inherit the errexit behavior when inherit_errexit is enabled.
  5. Command substitutions, i.e. $(command), also inherit the errexit behavior when inherit_errexit is enabled, BUT it does not cause the script to exit if it's a part of variable declaration or command argument. It ONLY causes error if it is a part of variable assignment.

The final exit status of the script, or any sub-shell or function inside, is determined by the last statement executed, before the script, sub-shell, or function exits.

So if this last executed command is a short-circuited logical compound statement that yield non-0 exit status, then the final exit status will also be non-0. This is a false negative as it is a valid branching decision. To mitigate this, ALWAYS have explicit exit or return statement with proper exit status at the end of script, sub-shell, or function. Or simply add a true command at the end to ensure the final exit status is 0.

These can be annoying, but the benefits of catching errors early outweigh the inconvenience. So when writing the script, always account for these behaviors to avoid unexpected script exits.

See below for an example script that demonstrates these behaviors, and how to mitigate them.

Script File
#!/bin/bash
set -euxo pipefail; shopt -s inherit_errexit

function MayFailFuncBad () {
 # Any command failure inside this function will cause the script to exit immediately.

 # If the `external-command` exit status is non-0, it does NOT cause the script to exit, because it is a part of variable declaration.
 typeset cmdPrintout="$(external-command)"

 # If the `external-command` exit status is non-0, it does NOT cause the script to exit, because it is a part of command argument.
 echo "$(external-command)"

 # If the `external-command` exit status is non-0, this function execution stops here and this function yield non-0 exit status as well.
 cmdPrintout="$(external-command)"

 case $cmdPrintout in
 (OK) echo 'Success';;
 (*)
  (
   # Enabling `inherit_errexit` causes the sub-shell to inherit the `errexit` behavior from the shell / parent process.

   # Any command failure that cause logical compound statement to short-circuit with non-0 exit status, will not cause the script to exit.
   false && true # The exit status of this statement is 1, but the script continues in this case.

   # But if the last command in logical compound statement fails, the script will still exit.
   true && false # The exit status of this statement is 1, and the script exits with failure.
  ) || true # Prevent the function from exiting due to the sub-shell or prev. command failure.

  # If `cmd1` exit status is non-0, this logical compound statement yields non-0 exit status. BUT since there is no more commands in this function after
  # this, the function will still exit with exit status of the last executed statement, which is non-0. Hence the caller will see this function as
  # failed and depending on the composition of the caller statement, this may cause the script exits with failure too.
  # And this is very hard to catch, because this is inside `case` statement, hence it is NOT apparent that this can actually be the last executed
  # statement in this function.
  cmd1 && cmd2
  ;;
 esac
}

function MayFailFuncGood () {
 if cmdA; then
  # If `cmdB` fails, the function does NOT exit with failure, even though this logical compound statement yields non-0 exit status. Because by having
  # `true` command at the end, that means there is more statement to be executed after this. And the function will continue executing, hence ensuring
  # that the function does not exit with failure due to short-circuiting.
  cmdB && cmdC
 else
  cmdD
 fi

 true
}

MayFailFuncBad || MayFailFuncGood

true

nounset Behavior

When nounset is enabled, it is very important to always declare shell variables (both global and local) before using them. For variables that are defined outside the script, such as environment variables, it is best to provide default values using parameter expansion syntax, e.g. ${ENV_VAR:-defaultValue}, to avoid unexpected script exits due to unset variables being used.

For system environment variables that are guaranteed to be set, such as HOME, PATH, PWD, etc., it is safe to use them directly without default values.

Or if the execution environment is well-controlled, such as in CI, and certain environment variables are always set, then it is also safe to use them directly.

Script File
#!/bin/bash
set -euxo pipefail; shopt -s inherit_errexit

typeset shellVar="${ENV_VAR:-defaultValue}"
echo "${shellVar}"

true

Functions

Use functions to encapsulate logic and improve readability. This makes it easier to understand and maintain the script.

But avoid overusing functions for very simple tasks that can be accomplished with a single command or a small block of code and ONLY used once. Overusing functions can make the script harder to read and understand.

Use consistent naming convention (stick with one convention throughout the script), that is DIFFERENT than variable naming convention:

  • Use PascalCase (preferred, it is shorter) or Capital_Snake_Case.

xtrace and Logging

When xtrace is enabled, avoid using commands like echo, printf, etc. for regular output, as it will clutter the log with redundant information. Generally speaking, since xtrace will print the processed statement, just before it got executed, to STDERR, the script execution flow would have been apparent.

For source-code documentation only, use a # comment — it has zero runtime effect and does not appear in xtrace output at all, keeping the log clean.

If a genuine runtime marker in the log is truly needed (e.g., to label a block whose individual commands are opaque at the xtrace level), use dummy commands like : as no-op operations. But try to avoid it if not strictly necessary, as it still produces a trace line that clutters the log.

Script File
#!/bin/bash
set -euxo pipefail; shopt -s inherit_errexit

# Preferred: `#` comment documents intent; zero runtime effect, invisible in xtrace.
# Starting operation XYZ...
...operationXYZ...

if [ someCondition ]; then
 # Only use `: "..."` when a runtime marker in the log genuinely adds value.
 : "Starting operation XYZ..." # Appears in xtrace as: + : Starting operation XYZ...
 ...operationXYZ...
 : "Completed operation XYZ."
fi

true

Variables

Handling and using variables properly is crucial for writing robust shell scripts:

  • Always declare variables (for both global and local variables) with proper type and initialize its value before using it. Use common variable declaration keyword, such as typeset, for better compatibility with different shell interpreters, or declare if the script is guaranteed to run in bash. Avoid using local for local variable declaration as it is not supported in all shell interpreters.
  • Prefer to use Shell Variables instead of Environment Variables. Environment Variables are more easily exposed (as they are inherited by child processes and in some CI environments, debugging information may include process Environment Variables) and have limited storage in the Process Context.
  • Use meaningful variable names to improve code clarity, but not overly long. Re-use commonly used variable names across scripts for consistency. Re-use generic variable names, such as loop variables.
  • Use consistent naming convention (stick with one convention throughout the script), that is DIFFERENT than function naming convention:
    • Use camelCase (preferred, it is shorter) or snake_case for shell variables.
    • Use UPPER_CASE for environment variable names.
    • Prefix boolean variables with is, has, should, etc.
    • Suffix (associative) array variables with Arr or at least have this tag as part of variable name.
  • Always use formal var. syntax inside a pair of double-quote, e.g. "${shellVar}", for safer handling in case the variable's value contains whitespace or special characters that need to be escaped.
  • Assign function arguments to local variables within the function for better readability.
  • Always use local variables within a function, to improve code modularity and avoid unintended side effects on global or outer scope variables. Pass them as parameters to the function, if needed.
  • Assign function return values to variables rather than modifying global or outer scope variables within functions (or use nameref).
  • Prefer using (associative) arrays for collections of related data instead of concatenated strings.
  • Prefer using inline Environment Variable assignment method, if it is only used by a single child process (e.g., VAR=value command). However, if the Environment Variable contains a secret, use normal assignment while temporarily disabling xtrace to avoid exposing the secret, then unset it after being used.
Script File
#!/bin/bash
set -euxo pipefail; shopt -s inherit_errexit

typeset optStrPar="${1:-}"; (($#)) && shift
typeset -i optIntPar="${1:-0}"; (($#)) && shift

typeset globalStrVar='Global String'
typeset -i globalIntVar=0
typeset -a globalArrVar=()
typeset -A globalAssocArrVar=()

function FooFunc () {
 typeset localStrVar='Local String'
 typeset -i localIntVar=1
 typeset -a localArrVar=()
 typeset -A localAssocArrVar=()

 BarFunc "${localStrVar}" "${localIntVar}" localArrVar

 true
}

function BarFunc () {
 typeset manStrPar="${1}"; (($#)) && shift
 typeset -i manIntPar="${1}"; (($#)) && shift
 typeset -n nameRefPar="${1}"; (($#)) && shift

 nameRefPar+=("${manStrPar}-Item${manIntPar}") # Update outer scope array via name reference.
 echo "${manIntPar}"

 true
}

globalIntVar="$(BarFunc "${globalStrVar}" 0 globalArrVar)"
FooFunc

set +x; export ONE_TIME_ENV_SECRET_VAR='secret-value'; set -x
ONE_TIME_ENV_VAR_1='some-value' \
 ONE_TIME_ENV_VAR_2="${optStrPar}" \
 external-command
unset ONE_TIME_ENV_SECRET_VAR

true

Output Redirection

If the STDOUT of a command is not needed, redirect it to /dev/null to avoid cluttering the output and improve performance. This is especially important in CI environments where excessive output can lead to timeouts or log size limits.

But NEVER redirect STDERR to /dev/null, as it may hide important error messages that may be crucial for post-mortem analysis.

Handling Secrets

Handling sensitive data (secrets), such as passwords, API keys, tokens, etc., require special care to avoid accidental exposure:

  • Store secrets in an ephemeral storage and ensure they will not linger after the session is completed.
  • Avoid hard-coding secrets directly in the script. Instead, read them from secure storage or environment variables at runtime.
  • Some execution environments, such as CI, have a good secret masking. But if this is not the case, ensure the secrets in logs and outputs (STDOUT, etc.) are not printed to prevent accidental exposure during debugging or monitoring.

Execution environment WITH masking capability

  • Preferred to store the secret in the smallest unit. Say split to crdUsr and crdPwd, instead of a combined crdUsrPwd. This allows flexibility to use in different syntax such as --cred "${crdUsr}:${crdPwd}" or --user "${crdUsr}" --pass "${crdPwd}".
  • If the credential is available in a temporary (provided by some kind of secret manager) file form, do NOT parse them then store them in variables. Because the system secret masking may not be able to detect and mask them. Instead, use Shell Process Substitution to pass them directly to the command that needs it.

Extra caution MUST be taken when xtrace is enabled. If the setting of the secrets is done within the script, then we MUST disable xtrace temporarily (do NOT forget to re-enable afterwards) during the setting to avoid exposing the secret. It is preferred to handle this temporarily disabled xtrace in a sub-shell (to avoid explicit need to re-enable it), unless a change in the parent's context (e.g. updating Environment or Shell Variable value) is required for later in the code.

3. GitHub

Working With Fork Repository

General Guidance

  1. Write clear and concise Pull Request (PR) Description that accurately describe the PR. This will become Merge Commit Message, so other can easily understand the changes implemented by the PR without need to navigate to the PR itself.
  2. Write clear and concise Commit Messages that accurately describe the changes made. This helps reviewers understand the purpose of each Commit and makes it easier to track changes over time.
  3. Break down large changes into smaller, manageable Commits. This makes it easier for reviewers to review the changes and provides a clearer history of the development process.
  4. Avoid adding new files using git add . or git add -A. Instead, use git add ...filePaths... to add only the relevant files. This prevents accidental inclusion of unwanted files in the Commit. Definitely do NOT use those 2 commands to add updated tracked files. Instead, use git add -u.

Rebasing onto Upstream Repository Main Branch

To keep the Fork Repository up-to-date with the Upstream Repository, it is best to rebase the Fork Repository Main Branch onto the Upstream Repository Main Branch, rather than merging the other way around. This keeps the Commit History clean, linear, and reduces the risk of merge conflicts.

Rebase often and/or periodically on longer-lived Pull Requests (PRs) to reduce the risk of conflicts and makes the process smoother.

Follow these steps to rebase the Fork Repository PR / working Branch onto the Upstream Repository Main Branch:

Terminal
# From GitHub Web UI, synchronize the Fork Repository Main Branch with the Upstream Repository Main Branch.
# WARNING:
# NEVER synchronize the Fork Repository PR / working Branch directly with the Upstream Repository Main Branch using the GitHub Web UI, as it will merge
# new changes from the Upstream Repository Main Branch into the PR / working Branch, which complicates the Commit History and may cause issue later if
# we want to squash the intermediary Commits.
git switch main && { { git pull -p --rebase || { git rebase --abort 2> /dev/null; git switch -; false; }; } && git switch - && { git rebase main || echo '^^^ Rebase FAIL!!!'; }; } || echo 'Working Tree is NOT clean!!!'

Squashing PR Commits Before Merging To Upstream Repository Main Branch

Inside a Pull Request (PR), often there are a significant number of Commits that are made during development and testing. Before merging the PR to the Upstream Repository Main Branch, it is best to squash these Commits into a single Commit that represents the entire PR change set. This is only needed if the Upstream Repository does not enforce Allow squash merging as the sole PR merge strategy. If the Repository already enforces it, this step can be skipped.

The advantages of doing this are:

  • Keeps the Upstream Repository Main Branch Commit History clean and easy to understand.
  • Makes it easier to revert the entire PR change set if needed.
  • Keeps the Upstream Repository size small.

Follow the git rebasing steps, with one additional step before the final push, to rebase the Fork Repository PR / working Branch onto the Upstream Repository Main Branch and squash the PR Commits:

Terminal
 ...FollowGitRebasingOntoUpstreamUpToGitCommit...
git rebase -i main # Squash ALL Commits to generate a single Commit.
git push --force-with-lease origin HEAD

Pull Request Workflow

The core GitHub Repositories uses CodeRabbit AI Code Reviewer. However, not all are part of Red Hat Enterprise Organization, so it only gets the free tier. This means, there is rate limit on PR Reviews (note: the exact limits below may change; verify at CodeRabbit - Plans and pricing):

  • 3 reviews /hour /user
  • 150 files /hour /user

If any of those limits are met, your push to the PR will not be reviewed.

Please follow below workflow to minimize the hitting the free tier limits and also to reduce the no. of Commits in the PR.

  1. Do not open the main PR (towards Upstream Branch) until it is considered ready. Keep pushing to the Fork Feature Branch only without creating PR. CodeRabbit only review pushes on PR.
  2. Perform local review (beware that CodeRabbit also has (separate) rate limit for local review) first using CodeRabbit CLI.
  3. If collaboration with other is needed, open auxiliary PR on the Fork Repository instead (from Fork Feature Branch towards Fork Branch that is synchronized with the Upstream Branch) and collaborate on this aux. PR. Do not install CodeRabbit in the Fork Repository. Close this aux. PR at the end of collaboration.
  4. When the work is ready, or at least mature enough, create the main PR. Once this main PR created, any push to Fork Feature Branch will be visible on the main PR and it may trigger CodeRabbit Review on the Upstream Repository and will consume the user free bucket.

    Below are the alternatives to mitigate CodeRabbit draining the user free bucket unnecessarily:

    • Tell CodeRabbit not to do Review on the main PR. Do one of the following:
      • Mark the main PR as Draft.
      • Put word WIP on the main PR.
      • Put statement @coderabbitai ignore in the main PR Description.
    • Be mindful on pushing Commits to Fork Feature Branch. Keep small Commits as local Commits only. Squash UN-PUSHED Commits into single Commit, before pushing it to Fork Feature Branch.

      Tip: Prefix the 1st line of Commit Message for all local Commits with a consistent identifier, e.g. lcl--, for easy identification when squashing the un-pushed local Commits.

    • Set the Fork Repository to have linear history (GitHub Repository: ONLY select "Allow squash merging" on PR Settings).

      Create a separate incremental Fork Feature Branch to receive further Commits from local Repositories. Create aux. PR on the Fork Repository (from incremental Fork Feature Branch towards actual Fork Feature Branch). Merge the aux. PR to actual Fork Feature Branch (a single Commit on Fork Feature Branch should be created if the PR Settings is set as per above).
